# GuelmaHistory Admin — Flutter Roadmap

## 1. Goal

Build a secure Flutter administration application for Android and iOS that works alongside the existing Nuxt 4 and Vuetify 4 web administration interface.

Both administration clients must use the same Nuxt/Nitro backend:

```text
Nuxt 4 + Vuetify 4 web admin ─┐
                              ├─ HTTPS ─ Nuxt/Nitro API ─ PostgreSQL/Drizzle
Flutter Android/iOS admin ────┘                         └─ Cloudinary
```

Flutter must never connect directly to PostgreSQL, Drizzle, Cloudinary administration credentials, or other private services. Authorization, validation, publishing rules, and media processing remain server-side.

The first mobile release is admin-only. Additional editorial roles should be introduced only after their permissions are formally designed in the backend.

## 2. Current GuelmaHistory baseline

The mobile application must follow the existing application rather than assume an unrelated CMS model.

Current stack:

- Nuxt 4 full-stack application with Nitro server routes
- Vue and Vuetify 4 web interface
- TypeScript
- PostgreSQL with Drizzle ORM
- `nuxt-auth-utils` sealed cookie sessions for web authentication
- Cloudinary for article media
- Zod-backed server validation
- Arabic and French localization

Current roles:

```text
user < author < admin
```

Current admin capabilities include:

- Admin authentication and profile management
- Article listing, creation, editing, deletion, counts, and recent articles
- Arabic and French article content
- Article image/video uploads
- Categories
- Authors
- Reported-comment handling
- Subscriber listing, status management, export, and cleanup

Current article fields include Arabic/French titles, excerpts and bodies, slug, cover image variants, home position, category, author, owner, publication date, reading time, views, and comment count.

## 3. Architecture rules

### One backend and two clients

Do not create a second backend for Flutter. Extend the Nuxt/Nitro API where mobile requirements are missing.

### Version mobile contracts

Expose stable routes under a versioned namespace where practical:

```text
/api/v1/admin/auth/*
/api/v1/admin/articles/*
/api/v1/admin/categories/*
/api/v1/admin/authors/*
/api/v1/admin/comments/*
/api/v1/admin/subscribers/*
/api/v1/admin/profile/*
```

Existing web endpoints may remain while versioned contracts are introduced incrementally. Business logic should live in shared server services so old and new handlers do not duplicate it.

### Consistent API responses

Every mobile endpoint should use predictable JSON responses, validation errors, pagination, and HTTP status codes.

```json
{
  "data": [],
  "meta": {
    "page": 1,
    "pageSize": 20,
    "total": 0,
    "hasNextPage": false
  }
}
```

Errors should include a stable machine-readable code and a safe human-readable message.

### Server-side authority

Flutter may hide unavailable actions for usability, but the Nitro server must independently enforce permissions for every request.

## 4. Repository strategy

Keep Flutter in a separate repository, for example:

```text
guelmahistory-admin-flutter/
```

This keeps Dart tooling, Android/iOS signing, release assets, and native dependencies separate from the Nuxt application. API contracts are shared through OpenAPI documentation rather than copied TypeScript code.

Use development, staging, and production environments. Never commit secrets or hard-code production URLs throughout the Dart source.

## 5. Milestone 0 — Backend readiness

Complete this milestone before building substantial Flutter screens.

### API inventory

- [ ] Document every existing admin endpoint, method, payload, response, and permission
- [ ] Identify endpoints used only by browser pages
- [ ] Add stable API error codes
- [ ] Standardize list pagination, filtering, and sorting
- [ ] Document upload MIME types, size limits, and progress behavior
- [ ] Add OpenAPI documentation for mobile-supported endpoints
- [ ] Verify production HTTPS and host configuration
- [ ] Review API rate limits separately for login, reads, writes, and uploads
- [ ] Confirm that server validation covers every Flutter write operation

### Mobile authentication

The current web application uses sealed cookie sessions. Keep that behavior for Nuxt web clients, but add a dedicated mobile authentication transport.

Recommended design:

- Short-lived access token
- Rotating refresh token
- Hashed refresh-token records stored server-side
- One refresh-token family per device/session
- Refresh-token reuse detection
- Device/session revocation
- Logout current device
- Logout all devices
- Password changes revoke other mobile sessions
- Current account and permission endpoint

Flutter stores refresh credentials only in Android Keystore/iOS Keychain-backed secure storage. Access tokens should preferably remain in memory and must never be logged.

Update the shared server authentication guard so protected domain services can be reached through either a valid Nuxt web session or valid mobile credentials without weakening role checks.

Do not use a long-lived bearer token without rotation and revocation.

### Initial mobile API scope

- [ ] Login, refresh, logout, current session
- [ ] Dashboard counts and recent articles
- [ ] Article CRUD
- [ ] Category CRUD
- [ ] Author CRUD
- [ ] Existing media upload
- [ ] Reported-comment listing and resolution
- [ ] Subscriber listing and management
- [ ] Admin profile and password management

### Backend verification

- [ ] Unit tests for token rotation and revocation
- [ ] Integration tests for authentication and role enforcement
- [ ] Contract tests for supported endpoints
- [ ] Upload tests for invalid type, oversized files, and authorization
- [ ] Verify the Nuxt web admin still works unchanged

## 6. Milestone 1 — Flutter foundation

Use a feature-first, easy-to-follow architecture:

```text
lib/
├── app/
│   ├── app.dart
│   ├── router.dart
│   └── bootstrap.dart
├── core/
│   ├── api/
│   ├── auth/
│   ├── config/
│   ├── errors/
│   ├── storage/
│   ├── theme/
│   └── localization/
├── shared/
│   ├── models/
│   └── widgets/
└── features/
    ├── authentication/
    ├── dashboard/
    ├── articles/
    ├── categories/
    ├── authors/
    ├── comments/
    ├── subscribers/
    └── profile/
```

Recommended dependencies:

- Riverpod for state and dependency management
- GoRouter for routing and guarded navigation
- Dio for API requests, cancellation, and upload progress
- Freezed and `json_serializable` for immutable models and JSON mapping
- `flutter_secure_storage` for mobile credentials
- Material 3 as the component foundation

Do not mix state-management systems. Do not place raw HTTP requests in widgets. Keep the flow straightforward:

```text
Widget → Controller/Notifier → Repository → API client → Nitro API
```

Configure:

- [ ] Development, staging, and production flavors
- [ ] Environment-specific base URLs
- [ ] Central API client and authentication interceptor
- [ ] Token refresh with single-flight protection
- [ ] Standard error mapping
- [ ] Request cancellation
- [ ] Production-safe logging
- [ ] Arabic and French localization
- [ ] RTL from the beginning
- [ ] Light, dark, and system themes
- [ ] Responsive navigation for phones and tablets

## 7. Milestone 2 — Authentication and application shell

Build:

- Login with username/email and password
- Show/hide password
- Loading, validation, network, and invalid-credential states
- Secure session restoration
- Automatic access-token refresh
- Expired/revoked-session handling
- Logout
- Responsive application shell
- Phone navigation and tablet navigation rail
- Admin profile and password change

Biometrics may later unlock locally stored credentials. Biometrics must not replace server authentication.

Definition of done:

- A verified admin can sign in, restart the app, restore a valid session, refresh credentials, and log out.
- Invalid, expired, reused, and revoked refresh credentials fail safely.
- Arabic, French, RTL, and accessibility behavior are verified.

## 8. Milestone 3 — Editorial MVP

Build only against fields and operations that currently exist.

### Dashboard

Show useful existing information:

- Article, author, category, and subscriber counts
- Recent articles
- Reported-comment count where available
- Quick action to create an article

Do not display fake analytics, review queues, schedules, or statuses.

### Article list

- Search
- Existing server filters and sorting
- Pagination or infinite loading
- Pull to refresh
- Article status derived only from real fields, such as published/unpublished
- Arabic/French title display according to app locale
- Edit and delete actions

### Article editor

The current article model is bilingual. The editor must support:

- Arabic title, excerpt, and body
- French title, excerpt, and body
- Slug
- Category
- Author/byline
- Cover image
- Article media
- Publication date
- Home position where authorized
- Validation matching the Nitro API

Use clear Arabic and French tabs or sections. Warn before leaving with unsaved changes.

Start with the content format already accepted by the Nuxt backend. Do not choose a Flutter rich-text document format that cannot be rendered consistently by the website.

### Existing supporting features

- Category CRUD
- Author CRUD
- Existing media upload with progress
- Reported-comment handling
- Subscriber management
- Admin profile

Definition of done:

```text
Login → create bilingual article → upload media → save → reopen → edit → publish/unpublish according to existing backend behavior
```

The result must be visible correctly in the Nuxt website and web admin.

## 9. Milestone 4 — Content safety and reliability

This milestone comes before expanding the historical CMS domain.

### Local draft protection

- Save unfinished editor state locally
- Restore drafts after process termination
- Preserve Arabic and French content independently
- Track the server article ID and last-known revision
- Encrypt or otherwise appropriately protect sensitive local draft data
- Remove local drafts only after confirmed synchronization or explicit discard

### Backend autosave

Add a dedicated autosave design rather than repeatedly sending uncontrolled full updates:

- Debounced saves
- Idempotency key where applicable
- Explicit save state
- Safe retries
- Validation without accidental publication
- Server timestamps and revision identifiers

### Conflict detection

Add an article revision/version field and require clients to submit the version they edited.

The server should return `409 Conflict` if another client saved a newer revision. Flutter must offer review/reload/reapply choices and must never silently overwrite newer server content.

### Upload reliability

- Retry failed uploads safely
- Prevent duplicate records on retries
- Recover after background/resume where practical
- Preserve metadata until upload confirmation

## 10. Milestone 5 — Backend domain expansion

These features do not currently exist completely and require database, service, API, Nuxt web-admin, and Flutter work.

Implement them one domain at a time.

### Editorial workflow

Design real states and transitions before changing UI:

```text
draft → in_review → scheduled → published → archived
```

Define who may perform each transition. Add scheduling workers and failure handling before presenting scheduled publishing in Flutter.

### Roles and permissions

Only add editor or moderator roles after defining a permission matrix and migration strategy. Prefer explicit permissions/capabilities if requirements become more detailed than the current role hierarchy.

### Historical references

Add structured references linked to articles with source type, title, author, publication, year/date expression, page, archive, URL, notes, and ordering.

### Timeline and historical periods

Support uncertain historical dates as structured data. Do not force approximate dates or ranges into fake precise timestamps.

### Media library

Separate reusable archival assets from article-specific media. Preserve originals and store metadata such as title, alternative text, caption, photographer, date expression, location, source, archive, collection, donor, copyright, usage rights, period, and notes.

### Comment moderation

Define moderation states and actions separately from the current comment-report/flag workflow. Preserve an audit history for moderation operations.

### Audit trail

Record sensitive actions server-side. Flutter and Nuxt may display the log, but neither client is the authoritative source.

## 11. Milestone 6 — Mobile capabilities

Add only after the core editorial experience and backend reliability are stable:

- Camera, gallery, and file picker uploads
- Push notification device registration
- Notification preferences
- Deep links with authentication guards
- Biometric local unlock
- Global search
- Offline read cache
- Carefully scoped offline write synchronization

Push notification delivery must originate from trusted server-side events. Never place provider secrets in Flutter.

## 12. Milestone 7 — Analytics and growth

Analytics require a real data source and privacy review.

Possible features:

- Views and visitors
- Top articles
- Traffic trends
- Category performance
- Device data
- Search activity

Do not manufacture analytics from article counters or display sample data as production information.

## 13. Design requirements

The product should feel historical, editorial, modern, and focused without fighting platform conventions.

Start with Material 3 core components. Extract reusable application components only when patterns repeat. Avoid building a large custom widget library before real screens establish the requirements.

Use design tokens for:

- Color
- Typography
- Spacing
- Radius
- Elevation
- Motion
- Icon sizes
- Touch targets

Required UX states for every screen:

- Loading
- Empty
- Error
- Success feedback
- Permission denied
- Session expired where relevant
- Offline behavior where relevant

Phone layouts should favor cards, bottom sheets, and focused full-screen editors. Tablets should use navigation rails and master/detail layouts where useful.

## 14. Arabic, French, and RTL

Arabic and French are first-class requirements.

Test:

- Arabic RTL layout
- French LTR layout
- Mixed Arabic/Latin content
- Arabic, French, and English keyboards
- Long historical names and citations
- Direction-aware icons
- Dialogs, sheets, forms, lists, and editor toolbars
- Large text and screen readers

Do not infer article language only from application locale; articles contain separate Arabic and French fields.

## 15. Security requirements

Before release verify:

- HTTPS everywhere
- No database, Cloudinary, signing, or backend secrets in Flutter
- Short-lived access credentials
- Rotating and revocable refresh credentials
- Secure credential storage
- Server-side role checks on every protected operation
- Rate limiting appropriate to each route type
- Upload MIME, signature, extension, and size validation
- Input validation and output sanitization
- No credentials or personal data in logs/crash reports
- Subscriber data is shown only where necessary
- Session/device management works
- Dependencies and native permissions are reviewed

Anything shipped inside a mobile binary must be considered discoverable.

- Permission tests

- Validation tests

- Upload security tests

### Flutter unit tests

- Repositories
- Controllers/notifiers

- Validation

### Flutter widget tests

- Login

- Article cards and forms
- Arabic/French editor switching
- Loading, empty, and error states

### Integration tests

```text

```

Also test expired sessions, network loss, process termination during editing, upload failure, and revision conflicts.

Testing must run locally with `flutter analyze`, `flutter test`, backend tests, and manual checks. This project does not rely on a pipeline for the requested workflow.

## 17. Android and iOS validation

Android:

- Back and predictive-back behavior
- System bars and safe drawing areas
- Keyboard resizing
- Photo/file picker and camera permissions
- Secure storage
- Notifications and deep links
- Background/resume and process death
- Mid-range physical devices

Apple platforms:

- iPhone safe areas and swipe-back behavior
- iPad responsive layout
- Keyboard behavior
- Photo/file picker and camera permissions
- Keychain
- Notifications and universal links
- Background/resume and process termination
- TestFlight builds on physical devices

Do not assume successful Android behavior guarantees successful iOS behavior.

## 18. Release and monitoring

Prepare application identifiers, signing, icons, splash assets, privacy declarations, store listings, screenshots, versioning, and production environment configuration.

Release gradually through Play internal/closed testing and TestFlight before production.

Monitor:

- Crashes
- Authentication and refresh failures
- API errors
- Failed saves and uploads
- Content conflicts
- App versions
- Backend health

Errors that risk content loss receive the highest priority.

## 19. Feature definition of done

A feature is complete only when:

```text
✓ Backend contract exists and is documented
✓ Server authentication and authorization are enforced
✓ Validation is shared conceptually across both clients
✓ Loading, empty, error, and success states exist
✓ Content-loss risks are addressed
✓ Arabic, French, RTL, and mixed text work
✓ Phone and tablet layouts are considered
✓ Android and iOS behavior is verified
✓ Accessibility is checked
✓ Tests pass locally
✓ No important analyzer warnings remain
✓ Nuxt web behavior has not regressed
```

## 20. Required implementation order

```text
1. Backend/API inventory
2. Mobile authentication and session management
3. Flutter foundation and localization
4. Login and responsive shell
5. Existing dashboard and article APIs
6. Bilingual article editor and existing media upload
7. Categories, authors, reported comments, subscribers, and profile
8. Local drafts, autosave, revisions, and conflict handling
9. Editorial statuses and expanded permissions
10. References, timeline, historical periods, and media library
11. Push notifications, deep links, search, and analytics
12. Security, accessibility, performance, store release, and monitoring
```

Protect historical content above everything:

```text
Data safety > correctness > security > usability > performance > visual polish
```
