# GuelmaHistory — Enable Nuxt/Nitro for Flutter Roadmap

## Purpose

Track the Nuxt 4 and Nitro backend work required to support the GuelmaHistory Flutter admin application without breaking the existing Vuetify 4 web admin.

```text
Nuxt/Vuetify web admin ─┐
                        ├─ Nuxt/Nitro API ─ PostgreSQL/Drizzle
Flutter Android/iOS ────┘                  └─ Cloudinary
```

Flutter must never connect directly to PostgreSQL, Drizzle, Cloudinary administration credentials, or other private services.

# MILESTONE 1 — Audit the Existing Nitro API

## Current system

The existing application already provides:

- Nuxt 4 and Nitro/H3 server routes
- PostgreSQL with Drizzle ORM
- Zod server validation
- `nuxt-auth-utils` cookie sessions
- Roles: `user < author < admin`
- Admin article, category, author, reported-comment, subscriber, and profile APIs
- Arabic and French article fields
- Cloudinary article media uploads

## Tasks

- [x] Inventory every `/api/admin/**` endpoint
- [x] Inventory administrator routes under `/api/auth/**`
- [x] Record request, response, query, error, and permission contracts
- [x] Identify handlers containing business logic that belongs in services
- [x] Document current pagination, search, filtering, and sorting
- [x] Document article media formats and upload limits
- [x] Document the article body format rendered by Nuxt
- [x] Confirm required Arabic and French fields
- [x] Confirm current publishing behavior based on `publishedAt`
- [x] Identify browser-only assumptions such as cookie authentication

## Verified audit findings

### Existing admin route groups

```text
/api/admin/articles
/api/admin/articles/:slug
/api/admin/articles/media/upload
/api/admin/authors
/api/admin/categories
/api/admin/comments/flags
/api/admin/profile
/api/admin/subscribers
/api/admin/upload
```

The administrator web login currently uses:

```text
POST /api/auth/login
POST /api/auth/logout
POST /api/auth/forgot-password
POST /api/auth/reset-password
```

Authentication is browser-oriented. Login creates a sealed `nuxt-auth-utils` cookie session with `setUserSession()`, protected routes read it with `getUserSession()`, and logout clears it with `clearUserSession()`.

### Authorization findings

Article write/list handlers and profile/report handlers inspected during the audit use `requireAdmin()`.

The audit originally found unguarded category, author, and subscriber management routes. Explicit `requireAdmin()` checks have now been added to the following handlers without changing their response contracts:

```text
GET    /api/admin/categories
GET    /api/admin/categories/count
POST   /api/admin/categories
PATCH  /api/admin/categories/:id
DELETE /api/admin/categories/:id
GET    /api/admin/authors
GET    /api/admin/authors/count
GET    /api/admin/authors/list
POST   /api/admin/authors
GET    /api/admin/subscribers
GET    /api/admin/subscribers/count
GET    /api/admin/subscribers/export
```

A second handler-by-handler pass added explicit `requireAdmin()` checks to:

```text
PATCH  /api/admin/authors/:id
DELETE /api/admin/authors/:id
GET    /api/admin/authors/by-slug/:slug
PATCH  /api/admin/authors/by-slug/:slug
DELETE /api/admin/authors/by-slug/:slug
PATCH  /api/admin/subscribers/:id/subscription
DELETE /api/admin/subscribers/:id
POST   /api/admin/upload
```

The legacy `/api/admin/upload` placeholder previously returned a misleading successful response without uploading anything. It is now protected and returns `501 Not Implemented`, directing article media clients to `/api/admin/articles/media/upload`.

A route being under `/api/admin` does not protect it automatically. All new admin handlers must include an explicit guard or use a future protected router/middleware mechanism with equivalent test coverage.

### Business-logic findings

Articles already have a dedicated `ArticleService` covering validation, relation checks, transactions, serialization, publishing side effects, media replacement, and Cloudinary cleanup.

Categories, authors, subscribers, profile operations, and reported-comment operations do not yet follow one consistent service structure. Several handlers or utilities access Drizzle directly. These domains require service extraction before versioned routes are added.

Current error responses are inconsistent:

- Article routes commonly pass errors through `toH3Error()`.
- Validation errors become one joined message without structured field errors.
- Some comment routes wrap results as `{ success, data }`.
- Other routes return arrays or domain objects directly.
- Unexpected production errors may currently expose `Error.message`.

### Pagination, filtering, and sorting

Article listing supports:

```text
page, limit, search, categoryId, category, authorId, tagId,
featured, status, sortBy, sortOrder
```

Article `limit` is capped at 100. Article status is inferred from `publishedAt`: non-null is `published`, null is `draft`.

The article response currently uses a `pagination` object with `currentPage`, `perPage`, `total`, `lastPage`, `hasNextPage`, and `hasPrevPage`. Other inspected admin lists return unpaginated arrays. The versioned API therefore needs a common pagination contract.

Article search currently applies only to `titleAr`, despite the bilingual model. This must be reviewed for Arabic/French mobile search.

### Article content and publishing

Creation currently requires both:

```text
titleAr, titleFr, bodyAr, bodyFr
```

Arabic and French excerpts are optional. Article gallery captions are also bilingual. Bodies are stored as strings, so Flutter must preserve the exact content format accepted and rendered by the Nuxt application.

There is no dedicated editorial status column. `publishedAt` is authoritative:

```text
publishedAt != null → published
publishedAt == null → draft
```

The first transition from null to a date triggers newsletter alerts. Mobile autosave must not set `publishedAt` accidentally.

### Media upload

`POST /api/admin/articles/media/upload`:

- Requires `admin`
- Accepts multipart field `file`
- Accepts declared `image/*` and `video/*`
- Has an endpoint limit of 100 MiB
- Has a Nuxt route-rule request limit of approximately 110 MB
- Uploads through server-only Cloudinary credentials
- Preserves an original image
- Generates WebP thumbnail, slider, and main variants with Sharp
- Returns image/video metadata including Cloudinary `publicId`

The current check trusts the multipart MIME declaration and does not implement idempotency. Those issues remain for Milestone 6.

# MILESTONE 4 — Add Secure Mobile Authentication

## Goal

Keep sealed cookie sessions for the Nuxt web admin and add a dedicated mobile authentication mechanism for Flutter.

Recommended mobile model:

- Short-lived access token
- Rotating refresh token
- Hashed refresh tokens stored in PostgreSQL
- One revocable session per device
- Refresh-token reuse detection
- Logout current device
- Logout all devices

Never store raw refresh tokens in the database or logs.

# Definition of Done

A Nitro feature is complete when:

```text
✓ Requirements and permissions are defined
✓ Database migration is safe
✓ Business logic lives in a reusable server service
✓ Nitro handler remains thin
✓ Zod request validation exists
✓ Authentication and authorization are enforced
✓ Stable response and error contracts exist
✓ Sensitive fields are not exposed
✓ Unit/integration tests pass locally
✓ Nuxt web admin is verified
✓ Flutter API contract is documented
✓ Arabic/French behavior is verified
✓ Retry and concurrency behavior are considered
✓ This roadmap is updated
```

Priority:

```text
Data safety > correctness > security > usability > performance > visual polish
```
